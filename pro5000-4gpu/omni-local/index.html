What is held constant, and what differs

Both runtimes use checkpoint f01e6a23ac60, seeds 0/1/2, eight denoising steps, 124 frames at 24 FPS and stereo audio. Their fine attention calls the same CAKE implementation with logical VSA block128. DiT compilation and reference memoization are disabled. These are custom CAKE deployments of both frameworks.

FastVideo uses its native /v1/videos/sync API at revision 089a5a55a000. References are pre-staged files in its native typed request format; the vLLM article measurements include multipart uploads of the identical bytes. End-to-end times include each server’s reference processing and MP4 response. Four-GPU FastVideo uses SP 4 with an unsharded text encoder; vLLM-Omni uses USP 4 and text-encoder TP 4. These are complete deployment measurements, not an isolated HTTP overhead test. Stage timer boundaries and native preprocessing can differ.

Data and reproducibility

  • The original five prompt/reference combinations are used, with their ordering preserved. Input URLs and prompt hashes are included in the JSON.
  • For each configuration, one warmup is excluded, followed by seeds 0, 1 and 2. The article specifies a three-seed mean but does not list all three seed values.
  • Every measured MP4 is checked for its dimensions, 124 frames, 24 FPS, and 32 kHz stereo audio. Model loading is outside the timing boundary.
  • Per-stage timings, individual request times, run states, memory samples and kernel evidence accompany the means. Displayed memory peaks are sampled at approximately 0.5-second intervals.

Sources and scope

This is an independent extension of the comparison by Hao AI Lab, not an official benchmark from the authors. Original device measurements and embedded demonstration videos are credited to FastH3 Omni Local. Model definitions come from the QAD model card and the NVFP4 decoder model card.
