SM120 native128 vs pinned FlashInfer64: comprehensive validation v2
================================================================
Baseline: FlashInfer f75bed5da7112103b75f82a4d4b5faf4be335154.
BF16 BSHD, D=128, exact original logical128 selection for both providers.
No CAKE quantized path and no Triton prototype substitution.

Correctness
-----------
45 native128 cases passed; FI passes 44 supported cases. The remaining
offset-address case is unsupported by pinned FI (requires 128-byte input
alignment); native128 supports the tested 16-byte-aligned offset.
31 cases check every Q row; long cases sample six boundary rows in EVERY
Q block plus 256 seeded random rows. All outputs are checked for finiteness
and exact repeatability. Reverse selected-index order and poisoned unused
indices are checked against the same oracle. The FI fused metadata adapter
is independently compared exactly with torch expansion/sort metadata.
FP32 oracle has TF32 disabled. Small cases use FP64 directly and record
FP32-vs-FP64 discrepancy. Numerical gates: output atol/rtol .01/.01,
relative L2 <= .005; natural-log LSE atol/rtol .002/.0002. Empty rows are
exactly zero output / -inf LSE. No tolerance was loosened for either kernel.
An initial harness failure was FP32-vs-FP64 disagreement under 8x Q/K
logits; using FP64 as the small-case authority resolved the oracle issue.
Original logs remain in correctness.json and correctness-fi64.json.

Runtime: 23 pytest cases passed, including graph replay changing all Q/K/V,
mask and sizes, overlapping graphs with different allocations, and input
GPU different from the current GPU. The last test exposed a DLPack device
guard bug; conversion now runs inside the existing device guard. GPU code
is unchanged. final-pytest.log records the post-fix run.

Performance
-----------
23 held-out shape/distribution cases, 21 interleaved paired rounds each.
Both providers are checked against the same oracle before timing.
Hot graph: 1 call/capture, 3 warm replays then 10 timed replays/sample.
Cold graph: 256 MiB read-modify-write cache flush before each single timed
graph replay, excluded from timing; GPU L2 is 96 MiB. This is a controlled
cache-flush experiment, not captured full-model activation traffic.
Kernel results use precomputed metadata and preallocated outputs.
Full-call results include allocations and compaction; FI now uses a fused
Triton128-to-64 expansion/scan, not the older torch repeat/sort adapter.
Eager host-inclusive timings, before/after GPU telemetry and raw samples
are retained. Clocks are not locked for standalone measurements.
Bootstrap intervals resample paired rounds within one process; they do not
constitute confidence intervals over machines or real model workloads.
9 representative wins/regressions repeated in a new process with a new
provider order. First run preceded the host guard fix; repeat followed it.

Decision
--------
Keep opt-in. Gains reproduce for the primary 8K/32K/41K, H14/56 cases,
but there are genuine regressions: H1, 1% random selections, single-block
selections, ragged sizes and the 16K scheduler boundary. Do not advertise
universal superiority or choose new tuning rules on this evaluation set.
Full FastH3 model activations, video quality and end-to-end speed remain
unverified. NCU mechanism/SoL evidence is in ../profile/native128-sol-audit/
(relative to the parent integration artifact directory).

Reproduction
------------
Use the saved run.py environment wrapper and minimax-h3-native/.venv/bin/python.
Command: validate_sm120_block128.py --mode correctness --output <new.json>
Command: validate_sm120_block128.py --mode performance --output <new.json>
For a repeat add --case-ids 1 3 5 6 8 10 11 13 20 --order-seed 87041.
GPU access in this session requires host execution outside the sandbox.
pre-commit was run; project deliberately excludes kernel files from lint.


Sanitizer coverage and limitation
--------------------------------
Compute Sanitizer 2025.3.1.0: memcheck, racecheck, synccheck each passed
four selected metadata/replay/concurrent-graph tests; zero reported memory
errors, race hazards or synchronization errors. CUDA API probe reports
were disabled (--report-api-errors no), as the existing empty-CuTe control
also triggers those probes. Memory/race/synchronization checks stayed on.

Uninitialized-output initcheck is NOT a clean pass. It reports BF16 output
reads after TMA stores. An isolated all-ones control reproduces 16,384
reports on BOTH native128 and pinned FI64, while both produce correct ones;
a PyTorch copy control reports zero. NVIDIA release notes document adding
cp.async.bulk initcheck support in 2025.4 and a related false-positive fix
in 2026.1, and still list unsupported tensor-map accesses. These observations
support a tool-coverage explanation, not a certificate of no uninitialized
reads. The repeated broad initcheck sweep was stopped after the controls;
its log is retained. Do not count this mode among the clean sanitizers.
https://docs.nvidia.com/compute-sanitizer/ReleaseNotes/index.html

A separate NaN-poisoned preallocated-output regression passes initcheck
with zero errors and checks that every output/LSE element is overwritten
correctly, including empty rows. This is one additional regression after
the 23-test full run; it does not replace uninitialized-allocation tracking.
See initcheck-nan-output.log and initcheck-control-{torch,native,fi}.log.
